# AAH Codebase Intelligence

Single skill that owns ALL codebase intelligence operations. Other skills invoke it
with the appropriate mode — they never write intel files directly.

## Output Directory

All artifacts are written to `.aah/codebase-intel/` (unified location for both
greenfield and brownfield projects).

## Modes

| Mode | Invoked by | What it does |
|------|-----------|--------------|
| `--mode import` (default) | Standalone or `aah-init-project` (brownfield path) | Full T0-T3 codebase scan, creates all 9 files |
| `--mode plan` | `/aah-plan` Step 8 | Reads plan artifacts, creates/updates intel with `[PLANNED]` markers |
| `--mode refresh --wave N` | `aah-build` Step 20 | Scans code changes from wave N, selective update of affected files |

## Files Produced (9 Total)

### Core 3 (always created/maintained)

|------|---------|
| `codebase-structure.md` | Module layout, directory structure, entry points, file organization, API routes |
| `dependency-map.md` | External dependencies (packages, versions, purpose) + internal module import relationships |
| `tech-stack.md` | Languages, frameworks, databases, infrastructure components, dev tools |

### Extended 5 (created when content warrants)

## Update Behavior (All Modes)

When intel files already exist and need to be modified — whether during plan mode
(brownfield), refresh mode (any wave after the first), or rework scenarios — follow
these rules to maintain structural integrity. **Never create disconnected duplicate
sections. Always integrate changes into the existing document structure.**

### General Principles

1. **Tables** — Insert new rows into the existing table. Never create a second table
   for the same data category.
2. **Mermaid diagrams** — Add new nodes, edges, or subgraphs into the existing diagram
   block. Never create a second diagram for the same architectural view.
3. **Directory trees** — Insert new entries at the correct hierarchy position in the
   existing tree. Never create a separate tree block.
4. **Lists / bullet points** — Add items to the existing list in the relevant section.
   Never create a duplicate section with the same purpose.
5. **Prose paragraphs** — Extend existing prose to incorporate new information inline.
   Never add a section with the same heading or overlapping purpose as an existing one.
6. **New sections** — Only create a new section when the content does not logically
   belong in any existing section (e.g., an entirely new architectural concern).

### Per-File Update Rules

| File | How to update in-place |
|------|------------------------|
| `architecture-diagram.md` | Add nodes/edges/subgraphs to the existing mermaid graph; add rows to the existing Layer Summary table; extend the existing External Integrations list |
| `codebase-structure.md` | Insert files/directories into the existing directory tree at the correct position; add rows to the existing Entry Points and API Routes tables |
| `dependency-map.md` | Add rows to the existing External Dependencies and Internal Module Dependencies tables |
| `tech-stack.md` | Add rows to the existing technology table in the appropriate category |
| `data-model-diagram.md` | Add entities/relationships to the existing ER diagram; add rows to the existing Key Entities and Data Stores tables |
| `data-flow-diagram.md` | Add steps/paths to the existing flow diagrams; add rows to the existing Data Pipelines and Integration Points sections |
| `dependency-graph.md` | Add nodes/edges to the existing dependency graph; update rows in the existing Coupling Analysis table |
| `codebase-learning.md` | Update relevant numbered sections in-place (e.g., add to §7 Key Abstractions, extend §3 Architecture Overview) |
| `codebase-profile.json` | Never modified by this skill (profiler script only) |

### Marker Placement

- Place `[PLANNED]` markers at the **item level** (on individual rows, nodes, or list
  items), not as section-level headers.
- Examples:
  - Table row: `| src.services.summarizer | anthropic, config | [PLANNED] orchestrator |`
  - Mermaid node: `SUMM[Summarizer Agent<br/>PLANNED - F026]`
  - Directory entry: `├── summarizer.py            # [PLANNED] F026`
  - List item: `- **Claude API**: ... response summarization [PLANNED]`

## Approach: Tiered Intelligence (Import Mode)

Not every file deserves the same analysis depth. The cost of understanding must be
proportional to the value of the intelligence. This skill follows a tiered model:

| Tier | What | How | Speed |
|------|------|-----|-------|
| T0 — Inventory | Every file: path, language, size, role classification | Profiler script (filesystem walk) | ~seconds |
| T1 — Skeleton | Source files: top-level symbols, imports, module graph | Profiler script (regex extraction) | ~seconds |
| T2 — Deep Extract | Key files: full understanding of entry points, APIs, data models, configs | Claude reads and analyzes files | minutes |
| T3 — Synthesis | Architectural patterns, design decisions, tech debt, mermaid diagrams | Claude reasons over T0-T2 data | minutes |

T0+T1 are automated via the profiler script. T2+T3 are where Claude's reasoning adds value.

### Step 2: Codemap Structural Index (MANDATORY)

Before running the Python profiler, create the codemap structural index. This provides
fast AST-level queries (symbols, call chains, impact analysis) used throughout AAH.

```bash
PROJECT_DIR=$(aah run core.common.config project-path)
DB_PATH="$PROJECT_DIR/.aah/codebase-intel/codemap.db"

# Verify codemap-scale is installed
uvx --from aah python -c "import codemap_scale; print(f'codemap-scale v{codemap_scale.__version__}')" || {
    echo "ERROR: codemap-scale not installed."
    echo 'uvx --from git+https://github.com/Deloitte-US-Consulting/ascend-agentic-harness.git aah install'
    exit 1
}

# Create structural index
codemap scout "$CODEBASE_ROOT" --db-path "$DB_PATH" --json

# Build semantic index (required for codemap ask)
codemap embed "$CODEBASE_ROOT" --db-path "$DB_PATH" --json

# Verify
ls -la "$DB_PATH"
codemap stats "$CODEBASE_ROOT" --db-path "$DB_PATH" --json
```

Write `codemap-metadata.json` to track indexing state (CRITICAL — orchestrator needs this):
```bash
STATS=$(codemap stats "$CODEBASE_ROOT" --db-path "$DB_PATH" --json)
aah run core.common.codemap_utils write-metadata \
  --project-path "$PROJECT_DIR" \
  --operation scout \
  --wave 0 \
  --stats "$STATS"
```

**WARNING:** If this step is skipped, the orchestrator will fire a redundant `codemap_scout`
during implementation because it checks `codemap-metadata.json` for freshness. This file
MUST exist after profiling completes.

### Step 3: T0+T1 Automated Profiling

Run the profiler script to get the foundational data:

```bash
PROJECT_DIR=$(aah run core.common.config project-path)
INTEL_DIR="$PROJECT_DIR/.aah/codebase-intel"
mkdir -p "$INTEL_DIR"

aah run core.intel.codebase_profiler \
  {codebase_root} \
  --output "$INTEL_DIR/codebase-profile.json" \
  --max-files 50000 \
  --max-parse 5000
```

Read the output JSON. This gives you:
- File inventory with language distribution and directory structure
- Top-level symbols (classes, functions, interfaces, types)
- Import/module dependency graph
- Detected frameworks and data stores
- Entry points, config files, API layer files, data model files
- Architectural layer classification and coupling analysis
- Hotspot files (most symbols = likely most complex)

### Step 4: T2 Deep Analysis

Based on the T0+T1 profile, read key files for deep understanding. Prioritize in this order:

1. **Entry points** — Read all files from `entry_points` in the profile (main.py, app.py, etc.)
2. **Config files** — Read `config_files` for project dependencies, build config, deployment setup
3. **API layer** — Read `api_layer_files` (routes, controllers, handlers) to understand the public interface
4. **Data models** — Read `data_model_files` (models, schemas, migrations, entities) for data structure
5. **Hotspots** — Read the top 5-10 files from `architecture.hotspots` for core business logic
6. **Coupling hubs** — Read files from `architecture.coupling.afferent_top` — these are the most depended-upon modules

For each file read, extract:
- What does this file do? (purpose)
- What are its key abstractions? (classes, functions, interfaces)
- What external systems does it interact with?
- What design patterns does it use?
- What are its dependencies and dependents?

Build a mental model of the system's architecture as you read.

## Mode: Plan

Creates or updates codebase intelligence from plan-phase artifacts. Invoked by
`/aah-plan` Step 8 after features, DAG, and waves are committed.

### Input Sources (read automatically)

- Feature files: `$AAH_DIR/plan/features/*.md` (file_scope, endpoints, dependencies)
- Architecture docs: `$AAH_DIR/architecture/*.md` (component relationships, data models, flows, API contracts, topology) + `$AAH_DIR/architecture/module-map.yaml` (module graph)
- Decision registry: `$AAH_DIR/discuss/decision-registry.yaml` (resolved technology & design decisions)
- Manifest: `$AAH_DIR/manifest.yaml` (stack_choices, project structure)
- DAG: `$AAH_DIR/plan/dag.json` (feature relationships)

### Behavior

```bash
PROJECT_DIR=$(aah run core.common.config project-path)
AAH_DIR="$PROJECT_DIR/.aah"
INTEL_DIR="$AAH_DIR/codebase-intel"
mkdir -p "$INTEL_DIR"
```

1. Read all plan artifacts listed above
2. Check if intel files already exist (brownfield case)
3. For each feature file (`.md`), extract `file_scope` to determine planned modules/files
4. From the architecture docs (`architecture-overview.md`, `module-map.yaml`), extract component relationships for architecture diagrams
5. From manifest `stack_choices`, extract tech stack and dependencies
6. From the architecture docs (`data-model.md`, `application-flow.md`, `api-interface-contract.md`, `agent-topology.md`), extract data models, integrations, and async flows

### Files to Create/Update

| File | Greenfield (create) | Brownfield (update in-place) |
|------|--------------------|--------------------|
| `codebase-structure.md` | Planned module layout from feature `file_scope` | Insert planned files into existing directory tree; add rows to existing tables |
| `architecture-diagram.md` | Prose architecture with embedded mermaid from the architecture docs | Add nodes/edges to existing diagram; add rows to existing tables |
| `dependency-map.md` | Packages from `stack_choices` + feature dependencies | Add rows to existing dependency tables |
| `tech-stack.md` | From manifest `stack_choices` | Add rows to existing tech stack table |
| `data-model-diagram.md` | Entity diagrams IF features define data schemas | Add entities to existing ER diagram |
| `data-flow-diagram.md` | Flow diagrams IF features define async/integration flows | Add paths/steps to existing flow diagrams |
| `dependency-graph.md` | Module relationship graph IF multiple modules planned | Add nodes/edges to existing dependency graph |
| `codebase-learning.md` | NOT created (no code to learn from) | NOT modified at plan time |
| `codebase-profile.json` | NOT created (requires Python profiler) | NOT modified |

### Rules

- If files already exist (brownfield): Follow the **Update Behavior** rules (§ above) —
  update existing sections in-place, never create disconnected duplicate sections
- If files don't exist (greenfield): CREATE from plan artifacts
- Mark ALL new projected entries with `[PLANNED]` markers at the item level (see Marker
  Placement in Update Behavior section)
- Only create extended files (data-model, data-flow, dependency-graph) when plan artifacts
  contain enough information to produce meaningful content
- Do NOT create `codebase-learning.md` or `codebase-profile.json` in plan mode
- For all diagram files, follow mermaid template patterns from
  `$(aah path)/_resources/_references/mermaid/diagram-templates.md`

## Mode: Refresh

Incremental update after a wave merge during the build phase. Invoked by
`aah-build` Step 20 after the wave summary is published.

### Input Sources (read automatically)

- Wave number from `--wave N` argument
- Features merged in this wave (IDs, names, `file_scope`) from feature-list.json and feature files (`.md`)
- Existing intel files in `$AAH_DIR/codebase-intel/`
- Actual source code changes introduced by the wave's features
- If rework wave: feedback context from `$AAH_DIR/build/feedback/{feature_id}-feedback.md`

### Behavior

```bash
PROJECT_DIR=$(aah run core.common.config project-path)
AAH_DIR="$PROJECT_DIR/.aah"
INTEL_DIR="$AAH_DIR/codebase-intel"
DB_PATH="$INTEL_DIR/codemap.db"
```

**Step 0: Update Codemap Index**

Before updating markdown artifacts, ensure the codemap structural index is current:

```bash
codemap update "$PROJECT_DIR" --db-path "$DB_PATH" --json
```

Use `codemap stats` to verify new symbols were indexed. Use `codemap impact` on changed
files to identify affected modules for targeted intel updates.

**Step 1-5: Intel Update**

1. Read the features merged in this wave (IDs, names, `file_scope`)
2. Read existing intel files in `$INTEL_DIR`
3. If any features in this wave have status "reworked", read the feedback that
   triggered the rework from `$AAH_DIR/build/feedback/{feature_id}-feedback.md`
4. Scan actual source code for changes introduced by the wave's features
5. Determine which intel files are affected and update only those

### Update Determination

The model determines which files need updating based on the wave's changes — no
hardcoded conditional logic. Use these as guidance (not control flow):

- `codebase-structure.md`: Update when new files/modules are created or existing
  ones restructured. Remove `[PLANNED]` markers. Note deviations.
- `architecture-diagram.md`: Update when new components, services, or architectural
  connections are introduced.
- `data-model-diagram.md`: Update when new data entities, schemas, or relationships
  are introduced.
- `data-flow-diagram.md`: Update when new request flows, async pipelines, or event
  sequences are introduced.
- `dependency-graph.md`: Update when new internal module dependencies or coupling
  changes occur.
- `dependency-map.md`: Update when new external packages are installed.
- `codebase-learning.md`: Update when major architectural changes affect patterns,
  conventions, or system purpose. Document the shift and rationale.
- `tech-stack.md`: Update when a fundamentally new technology is introduced.
- `codebase-profile.json`: NEVER update (requires Python profiler script).

### Rework Context

When the wave contains reworked features, feedback context is available that describes
WHY the architecture changed. Use this to understand the intent behind code changes
and update diagrams accurately rather than just inferring from code alone.

### Rules

- Follow the **Update Behavior** rules (§ above) for all file modifications — update
  existing sections in-place, never create disconnected duplicate sections
- Focus only on CHANGES from this wave — do not rewrite unchanged sections
- If actual implementation matches the projected plan, simply remove `[PLANNED]` markers
- If it deviates, update to reflect reality and note the deviation
- If a file doesn't exist yet but this wave's changes warrant it (e.g., first data
  entity created), create the file
- For diagram files, follow mermaid template patterns from
  `$(aah path)/_resources/_references/mermaid/diagram-templates.md`

### Output

This step does NOT commit separately — intel updates are included in the wave state
commit performed by the build skill (Step 20).

## Incremental Profiling (Import Mode)

If `.aah/codebase-intel/codebase-profile.json` already exists from a prior run, the skill
supports incremental updates:

1. Read the existing profile
2. Run the profiler script again (it's fast — seconds for most codebases)
3. Compare: new files, deleted files, changed files (hash comparison)
4. Update only the diagrams and learning doc sections affected by changes
5. Add a "Changes Since Last Profile" section to the learning document

## Adapting to Codebase Size (Import Mode)

| Size | Files | Strategy |
|------|-------|----------|
| Small | < 500 | Read most files. Diagrams can be very detailed. |
| Medium | 500-5K | Profile all, deep-read entry points + APIs + models + hotspots. |
| Large | 5K-50K | Profile all, deep-read top 50 files by role priority. Package-level diagrams. |
| Very Large | 50K+ | Profile with `--max-files 50000 --max-parse 5000`. Directory-level diagrams. Focus deep reads on the region the user cares about. |

For very large codebases, ask the user: "This is a large codebase ({N} files). Should I
profile the whole thing at a high level, or focus deeply on a specific directory/module?"
